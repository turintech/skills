# Report code metrics through Git

Use the supplied repository, branch and performance objective. Inspect the working tree and preserve unrelated edits. Work on a dedicated branch or worktree when appropriate. This workflow produces a Git branch for Artemis to import or select; it does not edit an existing Artemis changeset.

1. Inspect the build system, tests, CI and existing benchmarks. Ask about the workload or metric only when the repository and request do not establish it. Prefer adapting an existing harness.
2. Add the requested metric output to the code and commands the user already runs. A separate benchmark harness is optional; propose one only if the existing commands cannot produce useful measurements. Use repeatable inputs and preserve correctness checks. Keep dependency installation, compilation, data generation and warmup outside the timed region. Fail with a non-zero exit code for incorrect results or execution errors.
3. Put runnable wrappers in the repository. Document the exact root-level setup, benchmark and teardown commands. Setup builds and checks correctness; benchmark measures and may repeat; teardown cleans up. Do not assume an IDE, an interactive shell or an uncommitted dependency.
4. Use built-in Runtime, CPU and Memory command measurements where appropriate. For custom metrics, write fresh `artemis_results.json` or `artemis_results.csv` into the invocation directory (the project root). JSON accepts an object or array of objects; CSV has a header and numeric data rows. Values must be finite numbers, never strings, booleans, null or nested values. Keep names and units stable. JSON takes precedence when both files exist. Clear stale output before measurement and propagate failures when copying results from another directory.
5. Run the exact commands in a clean checkout with the required toolchain. Verify correctness and, when metrics are available, fresh numeric results and a repeatable second measurement. If the scripts work but measurements cannot yet be produced, preserve the working commands and logs, and report the missing metrics separately. Do not fabricate results or treat numbers printed in logs as recorded metrics. Keep generated results, caches, environments and secrets out of source control.
6. Review the intended diff. When committing and pushing are already authorised, commit the harness, necessary source changes and command documentation to the intended branch and push it. Otherwise leave the tested diff ready and ask only for the missing publishing authorisation. Never force-push or include unrelated changes.
7. Report the remote, pushed branch and full commit SHA. When `gitReturnUrlTemplate` is supplied, replace its placeholders with the URL-encoded branch and full pushed SHA, and return a clickable **Open prepared benchmark in Artemis** link. The app will offer changesets whose source branch and original SHA match, or explicitly create one from that external branch pinned to the commit. This does not require changing the project's default branch. Never use an unpushed SHA or claim that local measurements establish Artemis readiness. Without a template, construct `{deployment}/projects/{project-id}/settings/benchmarks/prepare?prepare=git&preparedBranch={url-encoded-pushed-branch}&preparedSha={full-pushed-commit-sha}` when those identifiers are available; otherwise explain the branch selection and sync steps in project settings.
8. In the returned Artemis branch, configure the documented root-level commands in Scripts, select a connected machine, and run the scripts. An older changeset's original version does not move when Git is pushed; keep the pinned commit and reuse its workspace for subsequent fixes. A successful run without recorded metrics still verifies execution. The user can then choose Discovery with script checks and Artemis Score; adding recorded metrics enables measured performance comparisons.

Explain the payoff: a correct, repeatable benchmark gives Artemis a measurable objective for comparing optimisation candidates. Local success is preparation evidence. Confirm script execution on the selected Artemis machine, and distinguish that success from whether performance measurements were recorded.

Finish with literal commands, metric names/units/directions, local verification evidence, Git branch/SHA, and the remaining Artemis validation step. Do not launch discovery or claim a measured optimisation as part of preparation.
