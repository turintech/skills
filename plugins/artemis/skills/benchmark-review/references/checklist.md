# Gap checklist

Walk every row while reading the benchmark. The fix column is a hint for you; tell the user the fix in their own terms. A row is a **gap** when the benchmark lacks it *for this goal*; a row that doesn't matter for the goal is not a gap. Rows marked **first** rank above the others when they are gaps, because a wrong answer there misleads the whole run. Never show the row numbers to the user.

| # | Check | First | What to look at | It's a gap when | Typical fix |
|---|---|---|---|---|---|
| 1 | The ranking metric is the goal | yes | The metric written to `artemis_results`, its unit and direction | It can improve while the goal doesn't (total time of setup plus work, a ratio, a proxy); the direction is unclear; it isn't per unit of work; startup vs steady state doesn't match what the user cares about | Report the goal's own number, per unit of work, with its direction stated |
| 2 | Nothing else gets worse unseen | yes | Other metrics and the gate | Something the user would mind (quality, memory, tail latency, size, a class of output) can get worse without any metric or gate noticing | Check it on every run, or measure it alongside |
| 3 | Inputs look like real use | yes | Where inputs come from, how many, which sizes | Inputs are toy-sized, uniform where real data is skewed, one fixed shape, or literals in the timed code; a regime the user judges apart (cold and warm, small and large, p50 and p99) is averaged into one number; the user runs several thread counts, precisions or flags and the benchmark scores only one | Real samples or a generator matched to them; the user's sizes plus one larger and one odd shape; report each situation the user cares about separately; each configuration the user runs as its own case |
| 4 | Correct means the same results as the original | yes | The test command and any in-benchmark check, against the rule for the output type ([traits.md](traits.md#equivalence-rules)) | Only some outputs or one input are checked; a tolerance is looser than it needs to be or unexplained; a class of output could vanish unnoticed; only stored golden files are compared; the candidate could read the reference's answer | Compare against the original implementation on every output, including inputs that aren't scored, under a stated rule |
| 5 | The timer is on the work | yes | What runs inside the timed region | The target isn't inside it; its result is never used, so the work can be skipped; setup, I/O or compilation dominate the time | Time until the output exists and is used; move setup out |
| 6 | The measurement can't be moved around | yes | Caches, files and processes between repetitions; thread and memory settings | Results can be cached between repetitions; work can move outside the timer (lazy results, import time); a version can use more cores or memory than the original | Fresh state each repetition; limits pinned in the command |
| 7 | Noise is known and repeats fit it | yes | Earlier validations or repeats of the Script; Benchmark runs per version | Noise was never measured, or it is larger than the smallest gain the user cares about; one run per version; a sample shorter than about a second | Measure the original several times; choose Benchmark runs from that; lengthen short samples |
| 8 | Warm-up is outside the timer | no | First iterations of the timed loop | JIT, autotune, cache fill or page-in land inside the timed numbers | Warm-up iterations before timing |
| 9 | Tuning data and checking data are apart | no (first for trained or fitted code) | Where a holdout lives; for trained or fitted code, where the split happens | No real data is kept back to check the best versions; for trained or fitted code, fitting touches test data, rows overlap, time-ordered data isn't cut by time, or a feature isn't known at prediction time | Keep some real data outside the repository and check the best versions on it afterwards; split before fitting |
| 10 | A broken version fails fast | no | The order of build, test and benchmark | A wrong version runs the full timed benchmark before anything fails | Correctness on small inputs before the full timing |
| 11 | Ways to win without a real gain | no | Everything above, read as a cheater would | A change could score better while doing the job worse: answers keyed on input names or sizes, reading the repository's expected outputs or models, a parser looser than real data needs, a fast path for one configuration that slows another | Name it to the user with its fix; platform-only holes are listed once, not as gaps to fix here |
| 12 | One version fits the time budget | no | Build, test and one benchmark run, times the repeats and versions | One version's evaluation is long enough that Discovery gets few versions in the user's budget | A quicker benchmark for comparing versions that keeps the real cases, with the full one for the best few |
| 13 | Discovery can aim | no | Target files, the metric's importance | Only a whole repository is in scope when the hot code is known; several metrics compete for the score, or reference timings and ratios are scored; the Script Discovery would run is a placeholder | Name the target files; one main metric, others secondary or unscored |
| 14 | It can be reproduced | no | Seeds, environment, commands | Seeds aren't fixed or logged; the runner or toolchain needed isn't stated | Log seeds; state runner and toolchain |
